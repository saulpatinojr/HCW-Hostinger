# Don't want to spend $$ on GitHub runners? Here's why Docker Compose is the right deployment unit

> **Vendor angle:** Docker, Docker Compose V2, container lifecycle, deployment patterns
> **Companion posts:** [Self-hosted runners in an afternoon](./01-github-self-hosted-runners.md) · [Idempotent VPS provisioning](./03-ansible-idempotent-vps-provisioning.md)

When you hear "deploy to a VPS," the mental model is often: SSH in, `git pull`, `systemctl restart app`. It works — until you have three services, they have dependencies, and you need to reproduce the whole thing on a new VPS in 10 minutes.

Docker Compose changes the unit of deployment from "commands to run" to "a file that describes desired state." This post is about why we chose it as the deployment primitive for our $8/mo self-hosted runner stack, and the specific decisions that made it work cleanly.

---

## The deployment unit problem

A deployment is really two things:

1. **What to run** — which image, which environment variables, which ports
2. **How to run it** — restart policy, resource constraints, network, volumes

Scripting this in bash is fragile. `systemctl` handles restarts well but not multi-container dependencies. Kubernetes handles everything but is massive overkill for one VPS.

Docker Compose is the middle ground. It describes the full desired state of a multi-container application in a single YAML file, and `docker compose up -d` converges the running system to match.

---

## V1 vs V2: use the plugin

Two versions of Compose exist. V1 (`docker-compose`, the Python binary) reached end-of-life in June 2023. V2 (`docker compose`, the Go plugin) is actively maintained and ships with Docker Engine.

The difference matters in practice:

```bash
# V1 — standalone binary, pip-installed, EOL
docker-compose up -d

# V2 — installed as docker-compose-plugin apt package
docker compose up -d   # note: space not hyphen
```

V2 container names also changed: `project_service_1` (V1) → `project-service-1` (V2). Any script filtering by container name needs to use the new format.

We install V2 via the Ansible `docker` role:

```yaml
- name: Install Docker Engine and Compose plugin
  ansible.builtin.apt:
    name:
      - docker-ce
      - docker-ce-cli
      - containerd.io
      - docker-buildx-plugin
      - docker-compose-plugin   # ← V2 plugin
    state: present
    update_cache: true
```

## The runner compose file

The GitHub Actions runner is fully described in a compose file generated by Ansible:

```yaml
services:
  runner:
    image: myoung34/github-runner:latest
    restart: unless-stopped
    environment:
      RUNNER_SCOPE: repo
      REPO_URL: "https://github.com/saulpatinojr/HCW-Hostinger"
      APP_ID: "{{ github_app_id }}"
      APP_LOGIN: "saulpatinojr"
      APP_PRIVATE_KEY: |
        -----BEGIN RSA PRIVATE KEY-----
        ...
      RUNNER_NAME: "vps-hostname"
      LABELS: "self-hosted,linux"
      RUNNER_WORKDIR: /tmp/runner/work
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - runner_work:/tmp/runner
    privileged: true

volumes:
  runner_work:
```

Three decisions buried in this file worth calling out:

### 1. `restart: unless-stopped`

Not `always`. `always` means the container restarts even after an explicit `docker compose stop` — making maintenance windows impossible. `unless-stopped` restarts on crash and on host reboot, but respects intentional stops.

### 2. Named volume, not bind mount, for work directory

`runner_work:/tmp/runner` is a Docker-managed named volume. Using a bind mount (`/host/path:/tmp/runner`) would require pre-creating the directory with correct ownership. Named volumes are created automatically with correct permissions.

The one exception: `/var/run/docker.sock` is a bind mount because it's a host socket, not a data directory. There's no way to "name" a socket.

### 3. Auth via environment variables

The GitHub App private key is passed as an environment variable (via Ansible template), not baked into the image or written to a config file on disk. This means rotating credentials is `ansible-playbook site.yml` — no SSH, no file editing, no service restart scripts.

## The deploy workflow

```yaml
# .github/workflows/multi-env-deploy.yml
jobs:
  deploy:
    runs-on: self-hosted
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v4
      - name: Deploy with Docker Compose
        env:
          NODE_ENV: ${{ github.ref == 'refs/heads/main' && 'production' || 'staging' }}
        run: |
          docker compose pull
          docker compose up -d --remove-orphans
          docker compose ps
```

`docker compose pull` downloads the latest image. `docker compose up -d --remove-orphans` starts new containers and removes any that no longer appear in the compose file. The three commands together do a rolling update with zero downtime for single-instance services.

`--remove-orphans` is the cleanup mechanism. If you rename a service in the compose file, the old container would otherwise keep running — `--remove-orphans` removes it.

## Concurrency: only the newest commit wins

Rapid pushes create a problem: three commits land in 30 seconds, three deploy jobs queue, all three run `docker compose up -d`. The second and third runs are racing to be the "winner" — and the winner is whichever finishes last, not the most recent code.

The fix is a concurrency group:

```yaml
concurrency:
  group: deploy-${{ github.ref }}
  cancel-in-progress: true
```

Only one deploy per branch runs at a time. New ones cancel in-progress predecessors. The newest commit always wins.

## What Compose gives you that scripts don't

| Concern | Bash deploy script | Docker Compose |
|---------|-------------------|----------------|
| Which image to run | Hardcoded or env var | Declared in file |
| Restart on crash | Must configure systemd separately | `restart: unless-stopped` |
| Env var management | Exported in script, easy to miss | Declared per-service |
| Multiple services | Multiple scripts | One `up -d` |
| Update to new image | `docker pull`, `docker stop`, `docker run` | `docker compose pull && docker compose up -d` |
| Rollback | Script in reverse, hope you remembered the old tag | `docker compose up -d` with previous compose file |
| State visibility | `docker ps` manually | Portainer reads the compose project |

The compose file is also the documentation. Anyone can read `docker-compose.yml` and know exactly what's running without SSHing in.

## Next steps

- **Pin image tags** — `myoung34/github-runner:latest` is convenient but unpredictable. Pin to a specific release once you've found a stable one.
- **Add health checks** — `HEALTHCHECK` in the compose file enables `docker ps` to show `healthy` vs `unhealthy`, and Portainer to alert on state changes.
- **Multi-service app** — when the placeholder nginx is replaced with a real app, Compose handles the database + app + cache dependency chain cleanly with `depends_on`.
